# Система управления приёмом лекарств

## 1. Описание предметной области

### 1.1. Назначение системы

Проект посвящён проектированию микросервисной информационной системы для управления процессом приёма лекарств пациентами медицинского учреждения.

Система предназначена для автоматизации работы врачей по созданию назначений, формирования расписания приёма лекарственных препаратов и контроля выполнения назначений.

Пациенты могут просматривать свои назначения и расписание приёма лекарств, получать напоминания и отмечать факт приёма препаратов. Врачи могут создавать назначения, контролировать соблюдение пациентами назначенного лечения и просматривать отчёты.

**Текущий результат проекта — проектная документация, архитектурные диаграммы и контракты взаимодействия. Реализация бизнес-сервисов и развёртывание инфраструктуры в рамках данного проекта не представлены.**

### 1.2. Акторы системы

| Актор | Описание | Основные возможности |
|---|---|---|
| Пациент | Пользователь, которому назначается лечение | Просмотр расписания, получение напоминаний, отметка о приёме лекарств, просмотр истории приёма |
| Врач | Медицинский специалист, назначающий лечение | Работа с пациентами, создание и изменение назначений, контроль соблюдения лечения, просмотр отчётов |
| Внешний Push/Email Provider | Внешняя система доставки уведомлений | Передача напоминаний пациентам через поддерживаемые каналы связи |

Аутентификация пользователей и управление учётными записями выполняются централизованно с помощью Keycloak.

### 1.3. Основные пользовательские сценарии

| № | Сценарий | Участник | Результат |
|---|---|---|---|
| 1 | Создание назначения лекарственного препарата | Врач | Новое назначение сохраняется в системе |
| 2 | Просмотр назначений пациента | Пациент, врач | Пользователь получает информацию о назначениях |
| 3 | Формирование расписания приёма | Система | Для назначения создаются записи расписания |
| 4 | Получение напоминания | Пациент | Пациент получает уведомление о предстоящем приёме |
| 5 | Отметка о приёме препарата | Пациент | Факт приёма фиксируется в системе |
| 6 | Отмена назначения | Врач | Назначение отменяется, связанные будущие операции обновляются |
| 7 | Просмотр статистики соблюдения назначений | Врач, пациент | Пользователь получает отчёт о выполнении назначений |

## 2. Доменные события и ограниченные контексты

### 2.1. Ограниченные контексты (Bounded Contexts)

В рамках проектирования предметная область разделена на шесть ограниченных контекстов. Каждый контекст отвечает за отдельную часть бизнес-логики и реализуется соответствующим микросервисом.

| Ограниченный контекст | Микросервис | Ответственность |
|---|---|---|
| Пациенты и врачи | `patient-service` | Хранение и управление информацией о пациентах и врачах |
| Лекарственные препараты | `medicine-service` | Ведение справочника лекарственных препаратов |
| Назначения | `prescription-service` | Создание, изменение, просмотр и отмена назначений |
| Расписание приёма | `schedule-service` | Формирование расписания, учёт приёма и пропусков лекарств |
| Уведомления | `notification-service` | Планирование, отправка и учёт доставки напоминаний |
| Отчётность | `report-service` | Формирование отчётов и статистики на основе данных системы |

Каждый микросервис владеет собственными данными. Прямой доступ к базе данных другого сервиса не допускается.

### 2.2. Доменные события

Для асинхронного взаимодействия микросервисов используется Apache Kafka.

В системе предусмотрены следующие доменные события:

| Микросервис-источник | Доменные события |
|---|---|
| `patient-service` | `PatientRegistered`, `PatientUpdated`, `DoctorRegistered` |
| `medicine-service` | `MedicineCreated`, `MedicineUpdated`, `MedicineDeactivated` |
| `prescription-service` | `PrescriptionCreated`, `PrescriptionUpdated`, `PrescriptionCancelled` |
| `schedule-service` | `ScheduleGenerated`, `ScheduleUpdated`, `ScheduleCancelled`, `MedicationTaken`, `MedicationMissed` |
| `notification-service` | `ReminderSent`, `ReminderDeliveryFailed` |

События передаются через Kafka в соответствии с согласованными контрактами. Общий конверт события содержит следующие поля:

- `eventId` — уникальный идентификатор события;
- `correlationId` — идентификатор для связи операций между сервисами;
- `eventType` — тип события;
- `schemaVersion` — версия схемы события;
- `occurredAt` — время возникновения события;
- `payload` — данные события.

### 2.3. Глоссарий предметной области

| Термин | Определение |
|---|---|
| Пациент | Пользователь медицинского учреждения, которому назначается лечение |
| Врач | Медицинский специалист, создающий назначения пациентам |
| Лекарственный препарат | Медицинский препарат, содержащийся в справочнике системы |
| Назначение (Prescription) | Указание врача на применение определённого лекарственного препарата пациентом |
| Расписание (Schedule) | Набор запланированных дат и времени приёма лекарств |
| Приём препарата | Подтверждённое пациентом выполнение запланированного приёма |
| Пропуск приёма | Ситуация, когда запланированный приём не был выполнен |
| Напоминание (Notification) | Уведомление пациенту о предстоящем приёме лекарства |
| Доменное событие | Сообщение о произошедшем изменении состояния или бизнес-действии в системе |
| Ограниченный контекст | Область предметной модели с определёнными границами и ответственностью |
| Проекция | Локальное представление данных, формируемое на основе получаемых событий |

## 3. Карточки микросервисов и варианты декомпозиции

### 3.1. Карточки микросервисов

| Микросервис | Ответственность | Основные данные | Взаимодействие |
|---|---|---|---|
| `patient-service` | Управление пациентами и врачами | Пациенты, врачи | REST API, события Kafka |
| `medicine-service` | Ведение справочника лекарств | Лекарственные препараты | REST API, события Kafka |
| `prescription-service` | Управление назначениями | Назначения пациентов | REST API, события Kafka |
| `schedule-service` | Формирование расписания и учёт приёмов | Записи расписания, статусы приёма | REST API, события Kafka |
| `notification-service` | Планирование и отправка напоминаний | Уведомления, история попыток доставки | REST API, события Kafka, внешний провайдер |
| `report-service` | Формирование отчётов и статистики | Локальные проекции данных | REST API, события Kafka |

### 3.2. Обоснование границ сервисов

Разделение выполнено по бизнес-ответственности. Каждый микросервис отвечает за определённую область предметной деятельности и управляет собственными данными.

Такое разделение позволяет независимо развивать отдельные части системы, уменьшает связанность компонентов и упрощает сопровождение.

### 3.3. Отвергнутые варианты декомпозиции

| Вариант | Причина отказа |
|---|---|
| Монолитное приложение с единой базой данных | Все функции и данные находились бы в одном приложении, что увеличивало бы связанность компонентов и усложняло независимое развитие отдельных частей системы |
| Разделение только на пользовательские роли (сервис пациента и сервис врача) | В одном сервисе оказались бы объединены разные бизнес-процессы: назначения, расписание, уведомления и отчётность |
| Объединение расписания и уведомлений | Формирование расписания и доставка напоминаний имеют разные обязанности и жизненные циклы |
| Объединение всех справочных и операционных данных в одном сервисе | Это смешивало бы управление пациентами, лекарствами, назначениями и учёт приёмов |

Выбранная декомпозиция обеспечивает разделение ответственности по основным бизнес-процессам предметной области.

## 4. Выбранное программное обеспечение

Для построения архитектуры выбраны следующие инфраструктурные компоненты и технологии.

| Компонент | Назначение | Обоснование выбора |
|---|---|---|
| Nginx | API Gateway, маршрутизация входящих запросов | Позволяет организовать единую точку входа и направлять запросы к соответствующим микросервисам |
| Keycloak | Аутентификация и управление доступом | Централизует управление пользователями и ролями, поддерживает OAuth 2.0 и OpenID Connect, выдаёт JWT-токены |
| Apache Kafka | Асинхронный обмен событиями | Позволяет организовать независимое взаимодействие микросервисов через события |
| PostgreSQL | Хранение данных | Реляционная СУБД с поддержкой транзакций и ограничений целостности |
| Push/Email Provider | Внешняя доставка уведомлений | Обеспечивает фактическую отправку напоминаний пациентам через внешние каналы связи |
| OpenAPI 3.0.3 | Описание REST API | Позволяет формализовать контракты взаимодействия и документировать операции сервисов |

### 4.1. Организация хранения данных

Для каждого бизнес-сервиса предусмотрена собственная база данных PostgreSQL.

| Микросервис | База данных |
|---|---|
| `patient-service` | `patient_db` |
| `medicine-service` | `medicine_db` |
| `prescription-service` | `prescription_db` |
| `schedule-service` | `schedule_db` |
| `notification-service` | `notification_db` |
| `report-service` | `report_db` |

Базы данных логически разделены по сервисам. Это не требует обязательного использования отдельных физических серверов PostgreSQL.

## 5. Архитектурная схема и взаимодействие сервисов

### 5.1. Архитектурная схема

Общая архитектура системы представлена на диаграмме:

- [Архитектурная схема микросервисной системы](docs/diagrams/Архитектурная_схема_микросервисной_системы.drawio)

На диаграмме показаны шесть бизнес-сервисов, инфраструктурные компоненты, базы данных и основные направления взаимодействия.

Nginx принимает входящие запросы и маршрутизирует их к микросервисам. Keycloak отвечает за аутентификацию пользователей и выдачу токенов. Kafka обеспечивает асинхронный обмен событиями. Каждый бизнес-сервис использует собственную базу данных PostgreSQL.

### 5.2. Диаграммы последовательности

Для демонстрации основных процессов подготовлены следующие диаграммы:

1. [Успешное создание назначения](docs/diagrams/Успешное_создание_назначения.drawio) — показывает проверку связанных данных, сохранение назначения, публикацию события и последующее формирование расписания и напоминаний.
2. [Сценарий со сбоем](docs/diagrams/сценарий_со_сбоем.drawio) — показывает обработку ошибки при создании назначения и прекращение дальнейшей обработки при неуспешной проверке данных.

### 5.3. Таблица взаимодействий микросервисов

| Инициатор | Получатель | Способ взаимодействия | Назначение |
|---|---|---|---|
| Клиентское приложение | Nginx | HTTP | Передача входящих запросов |
| Nginx | Бизнес-сервисы | HTTP | Маршрутизация запросов |
| Бизнес-сервисы | Keycloak | OAuth 2.0 / OpenID Connect | Использование механизмов аутентификации и проверки доступа |
| `prescription-service` | `patient-service` | REST API | Проверка существования пациента и врача при создании назначения |
| `prescription-service` | `medicine-service` | REST API | Проверка существования лекарственного препарата |
| `prescription-service` | Kafka | Публикация событий | Передача информации об изменениях назначений |
| `schedule-service` | Kafka | Получение и публикация событий | Формирование расписания и передача информации о приёмах |
| `notification-service` | Kafka | Получение и публикация событий | Создание напоминаний и передача результатов доставки |
| `report-service` | Kafka | Получение событий | Обновление локальных проекций для формирования отчётов |
| `notification-service` | Push/Email Provider | Внешний API | Фактическая доставка напоминаний |

Синхронное взаимодействие через REST API применяется там, где необходимо получить немедленный ответ, например при проверке существования пациента или лекарственного препарата.

Асинхронное взаимодействие через Kafka используется для передачи информации о произошедших событиях и запуска последующих процессов без необходимости ожидать их завершения в исходном запросе.

Прямое обращение одного микросервиса к базе данных другого микросервиса не предусматривается.

| Топик | Назначение |

| `schedule.events` | События расписания и приёма лекарств |
| `notification.events` | События доставки напоминаний |

| `PrescriptionCancelled` | `prescription.events` | `prescription-service` | `schedule-service`, `report-service` |

### 6.3. Описание схем событий

Общее описание событий, структуры сообщений, топиков и правил взаимодействия приведено в отдельном документе:

- [Описание Kafka-событий](events/events.md)

Каждое сообщение Kafka содержит общий конверт события с идентификаторами, типом, версией схемы, временем возникновения и полезной нагрузкой.

Для надёжности обработки событий предусматриваются идемпотентность потребителей и Transactional Outbox при публикации событий.

## 7. OpenAPI-контракты

Для документирования REST API каждого микросервиса подготовлен отдельный OpenAPI-файл версии 3.0.3.

| Микросервис | OpenAPI-файл | Назначение API |
|---|---|---|
| `patient-service` | [patient-service.yaml](api/patient-service.yaml) | Управление пациентами и врачами |
| `medicine-service` | [medicine-service.yaml](api/medicine-service.yaml) | Работа со справочником лекарственных препаратов |
| `prescription-service` | [prescription-service.yaml](api/prescription-service.yaml) | Управление назначениями |
| `schedule-service` | [schedule-service.yaml](api/schedule-service.yaml) | Работа с расписанием и отметками о приёме |
| `notification-service` | [notification-service.yaml](api/notification-service.yaml) | Просмотр уведомлений и повторная отправка |
| `report-service` | [report-service.yaml](api/report-service.yaml) | Получение отчётов и статистики |

В OpenAPI-контрактах описаны доступные операции, параметры запросов, структуры данных, ответы и возможные ошибки.

Для всех сервисов предусмотрена единая схема пагинации: нумерация страниц начинается с единицы (`page=1` — первая страница), размер страницы ограничен значениями от 1 до 100.

Для описания ошибок используется единая структура с обязательными полями `type`, `title`, `status`, `detail` и `instance`.

## Статус проекта

На текущем этапе подготовлены:

- анализ предметной области и основных пользовательских сценариев;
- выделение ограниченных контекстов;
- декомпозиция системы на шесть бизнес-сервисов;
- описание инфраструктурных компонентов и выбранных технологий;
- архитектурная схема и диаграммы последовательности;

Проект представляет собой архитектурную и контрактную основу для дальнейшей реализации микросервисной системы управления приёмом лекарств.
