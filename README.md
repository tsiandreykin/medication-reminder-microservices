# Система управления приёмом лекарств

## О проекте

Проект посвящён проектированию микросервисной информационной системы для управления процессом приёма лекарств пациентами медицинского учреждения.

Система предназначена для автоматизации работы врачей по созданию назначений, формирования расписания приёма лекарств и контроля выполнения назначений. Пациенты могут просматривать расписание, получать напоминания и отмечать факт приёма препаратов. Врачи могут контролировать соблюдение назначенного лечения и просматривать отчёты.

**Текущий результат — проектная документация и контракты взаимодействия.** Реализация бизнес-сервисов и развёртывание инфраструктуры в рамках данного проекта не представлены.

## Архитектура

В системе выделено шесть бизнес-сервисов. Каждый сервис отвечает за собственную предметную область и использует отдельную базу данных PostgreSQL.

| Сервис | Ответственность | База данных |
|---|---|---|
| `patient-service` | Управление пациентами и врачами | `patient_db` |
| `medicine-service` | Ведение справочника лекарственных препаратов | `medicine_db` |
| `prescription-service` | Создание, изменение, просмотр и отмена назначений | `prescription_db` |
| `schedule-service` | Формирование расписания и учёт приёмов лекарств | `schedule_db` |
| `notification-service` | Планирование, отправка и учёт напоминаний | `notification_db` |
| `report-service` | Формирование отчётов и статистики | `report_db` |

Сервисы не обращаются напрямую к базам данных друг друга. Для синхронного взаимодействия используется REST API, для асинхронного обмена событиями — Apache Kafka.

### Инфраструктурные компоненты

- **Nginx** — reverse proxy и единая точка входа для маршрутизации внешних запросов к бизнес-сервисам.
- **Keycloak** — аутентификация и управление доступом на основе OAuth 2.0 / OpenID Connect.
- **PostgreSQL** — отдельная база данных для каждого бизнес-сервиса.
- **Apache Kafka** — обмен бизнес-событиями между сервисами.
- **Внешний Push / Email-провайдер** — доставка напоминаний пациентам через `notification-service`.

Клиентское приложение взаимодействует с системой через Nginx, работающий как reverse proxy. Nginx маршрутизирует запросы к бизнес-сервисам и передаёт заголовок Authorization; проверка JWT выполняется сервисами с использованием Keycloak. Прямой доступ к базам данных других сервисов не предусматривается.

## Основные проектные решения

- Выделено шесть бизнес-сервисов с независимыми зонами ответственности.
- Каждый бизнес-сервис владеет собственной базой данных PostgreSQL.
- Клиентские запросы проходят через Nginx.
- Аутентификация и управление ролями вынесены в Keycloak.
- REST API используется для синхронных запросов и проверок данных.
- Apache Kafka используется для асинхронного обмена событиями.
- `report-service` строит отчёты на основе локальных проекций и событий, не выполняя прямые запросы к базам данных других сервисов.
- Для обработки повторной доставки событий предусматривается идемпотентность; для надёжной публикации событий используется Transactional Outbox.
